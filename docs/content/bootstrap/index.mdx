In the context of Dolos, we use the term _bootstrap_ to refer to the process of filling Dolos's stores with the current state of the chain, rather than syncing it block by block from genesis. The bootstrap command uses a subcommand to select the source:

```sh
dolos bootstrap <source>
```

| source | what it does |
| ------ | ------------ |
| `stelae` | restores a Stelae snapshot (a _stele_): minutes, from a stele you can verify |
| `mithril` | downloads a Mithril-certified ImmutableDB and replays it: hours, trusting Mithril's signers |
| `immutabledb --source <PATH>` | replays the ImmutableDB of a local Cardano node database: hours, from a database you hold |

If no source is given, an interactive prompt lets you choose; without a terminal, the command exits 1 instead. Every flag of every source is listed in the [CLI reference](../reference/cli#dolos-bootstrap).

Bootstrapping is optional. A node with empty stores syncs from genesis with `dolos daemon` (or `dolos sync catchup`), which takes from a few hours to several days depending on the network.

## Existing data

Every source refuses when any managed store already holds data, unless told otherwise:

| flag | description |
| ---- | ----------- |
| `--force` | Replace the data: the source's inputs are resolved and checked first, then the storage root is cleared |
| `--skip-if-data` | Exit 0 without bootstrapping when storage already holds a node |
| `--continue` | `mithril` and `immutabledb` only: resume an interrupted replay from its committed position, over the data it left |
| `--verbose` | Enable verbose logging output |

The first three exclude one another. A stele restore has no `--continue`: run an interrupted one again with `--force`.

A state or archive store this release refuses (see [store identity](../architecture/data-layer#store-identity)) stops the bootstrap under every flag but `--force`, which clears it. `--force` clears only the storage root, and never a state store that fails to open for another reason, as a half-unpacked one does, or whose cursor fails to read. So beside a refused store it is refused, naming what to remove by hand, while such a state is there, or while a directory the configuration keeps outside the root holds data: a store with data, an archive that fails to open, or block segments. A directory holding no data, such as a fresh mount point or an empty store this release opens, doesn't stop it. Stop the node first: a running node holds its stores, so they fail to open, and `--force` stops at the store's own error.
