In the context of Dolos, we use the term _bootstrap_ to refer to the process of updating Dolos with the current state of the chain. This is usually a long process that involves processing a lot of data. There are ways to speed up the process.

The bootstrap command uses subcommands to select the method:

```sh
dolos bootstrap <method>
```

If no method is specified, an interactive prompt will let you choose.

## Global Flags

These flags apply to all bootstrap methods:

| flag | description | default |
| ---- | ----------- | ------- |
| `--force` | Clear existing data before bootstrapping | `false` |
| `--skip-if-data` | Skip bootstrap if data already exists (exit 0); a store this release refuses is an error instead | `false` |
| `--continue` | Continue bootstrap even if data exists, trusting the subcommand to handle resumption | `false` |
| `--verbose` | Enable verbose logging output | `false` |

By default, `dolos bootstrap` will error if it detects existing data in storage. Use one of the flags above to control this behavior.

A state or archive store this release refuses (see [store identity](../architecture/data-layer#store-identity)) stops the bootstrap under every flag but `--force` on its own, which clears it. Given with `--skip-if-data` or `--continue`, which leave storage as it is, `--force` is refused too. And `--force` clears only the storage root, never a state store that fails to open for another reason, as one in use does. So beside a refused store it is refused, naming what to remove by hand, while the state fails to open, or while a directory the configuration keeps outside the root holds data: a store with data, an archive that fails to open, or block segments. A directory holding no data, such as a fresh mount point or an empty store, doesn't stop it.
