Dolos provides an HTTP endpoint to access data using [Blockfrost OpenAPI](https://github.com/blockfrost/openapi) specification.

## Usage

If enabled via configuration, _Dolos_ will expose a TCP port accepting HTTP connections. The default port number is `3000`, but this value can be changed via configuration.

Once you have the daemon running you can hit the endpoint using any HTTP client (cURL, Postman, your browser, etc).

This is an example of querying for the latest block using `curl`:


### Using the Blockfrost SDKs

Blockfrost's SDKs can (to the most part) be adapted to be used with the Dolos MiniBF endpoint.
An example with the [Python SDK](https://github.com/blockfrost/blockfrost-python/) looks like this:

```python
import json

from blockfrost import BlockFrostApi

api = BlockFrostApi(
    project_id=None,
    base_url="http://localhost:3000",
    api_version=None,
)
api.api_version = None  # The API version defaults to "v0" on __init__.

print(json.dumps(api.block_latest().to_dict(), indent=2))
```

### Using a Tx Builder

The endpoints required for most tx builders to work are supported. Libraries like Lucid, Lucid-evolution, Blaze, MeshJS, etc can be used by pointing their corresponding provider configuration to Dolos Mini-BF endpoint.

## Configuration

The `serve.minibf` section controls the options for the MiniBF endpoint that can be used by clients.

| property           | type             | default                                                |
| ------------------ | ---------------- | ------------------------------------------------------ |
| listen_address     | string           | required                                               |
| permissive_cors    | boolean          | `true`                                                 |
| public_url         | string           | none                                                   |
| token_registry_url | string           | none                                                   |
| max_scan_items     | integer          | `3000`                                                 |
| route_prefix       | string           | none                                                   |
| ipfs_gateways      | array of strings | `["https://ipfs.io", "https://gateway.pinata.cloud"]` |

- `listen_address`: the local address (`IP:PORT`) to listen for incoming connections (`[::]` represents any IP address).
- `permissive_cors`: allow cross-origin requests from any origin.
- `public_url`: the URL clients reach the API at, reported by the `/` root response.
- `token_registry_url`: token registry base URL used for off-chain asset metadata.
- `max_scan_items`: caps page-based scans for heavy endpoints.
- `route_prefix`: a URL path every endpoint is served under, `/health` and `/metrics` included; set `"/api/v0"` to match the Blockfrost server URL. It starts with `/` and names at least one segment, none of them empty; its segments use only letters, digits, `-`, `.`, `_` and `~`, and `.` and `..` segments are refused; a trailing `/` is dropped. A path outside the prefix answers like any unknown path. Unset, the endpoints are served at the root.
- `ipfs_gateways`: the gateways that resolve `ipfs://` governance-anchor URLs, tried in order; an empty list turns IPFS resolution off.

This is an example of the `serve.minibf` fragment with a `dolos.toml` configuration file.

```toml
[serve.minibf]
listen_address = "[::]:3000"
permissive_cors = true
token_registry_url = "https://token-registry.io"
public_url = "https://minibf.local"
max_scan_items = 3000
```

Check the [Configuration Schema](../configuration/schema) for detailed info on how to set this up.

## Lifetime totals and rolling history

`/addresses/{address}/total` and `/accounts/{stake_address}/addresses/total` read per-epoch sums from the Stats period logs rather than folding blocks. When `history.mode` is `rolling`, housekeeping prunes those logs by slot like any other, so the sums and `tx_count` only cover the epochs the retained window still holds. Keep `history.mode = "full"` if you need true lifetime totals.

## The script list and data synced by an earlier version

`/scripts` reads the first-script period logs the node builds while it rolls blocks: per epoch, the scripts it saw first, in the order cardano-db-sync first sees them, sealed into archive chunks once the epoch can no longer roll back. The archive's entity index, which the seal writes for every script of a sealed epoch, and the staged rows of the epochs not yet sealed tell a script's first sighting from a repeat. Data synced by a version without them has none for the blocks it already holds, so the list would start wherever the upgrade happened. An archive whose seals ran on an earlier version that kept the entity index but wrote no script entries to it holds the sealed lists, but nothing marks their scripts as seen: a script carried again after the upgrade is listed a second time, in the epoch of its new carrier, and a lookup by hash does not find a script sealed before the upgrade until it is carried again. Run `dolos doctor rebuild-state --rewrite-logs` (or bootstrap again) to build both from the start of the chain; a rebuild without `--rewrite-logs` reads the index as it finds it and fixes neither. The rebuild replays the archive from the first block, so it refuses an archive that a rolling `history` window has already pruned; such a node has to bootstrap again. The sealed chunks are archive logs, so a rolling `history` window prunes them by slot like any other: a pruned node lists the scripts first seen in the epochs its archive still holds. A stele snapshot published by such a version has no `first-scripts` state either; a restore refuses it by name rather than leaving the list empty, so bootstrap from a stele published by a version that carries them. A rolling `history` window also prunes the entity index by slot, so a script carried again after its first carrier left the window is listed a second time, in the epoch of its new carrier. A node without an archive keeps neither the sealed chunks nor the index, so it lists its unsealed epochs alone, a script first seen in an earlier epoch among them.

`/scripts/{script_hash}` and its `/json`, `/cbor` and `/utxos` variants answer for the scripts the list holds, the way Blockfrost does: a transaction that failed phase-2 validation contributes only the reference script of its collateral return, so a script only its witnesses or auxiliary data carried is in neither. A lookup reads the script from the block that counted it first, which the entity index or the staged rows name; a script in neither is not found, without walking the archive. Once a rolling `history` window prunes that block, the script is found again only if it is carried again inside the window.

pallas 1.3 decodes no Plutus V2 or V3 scripts in auxiliary data, so a script only auxiliary data ever carried in those languages is missing from the list.

## Asset reads and data synced by an earlier version

`/assets/{subject}`, the asset lists and `/addresses/{address}/extended` report each asset's supply, mint and burn count, first mint and the tx holding its on-chain metadata. No state namespace keeps them: the node folds them from the asset-mint period logs, keeping each asset's fold over the epochs no rollback can reach in the `assets` cache namespace, and adds the epochs after them on every read. A CIP-68 reference token's metadata tx is the newest output carrying it with a datum, or the newest mint whose CIP-25 metadata names it, read from the blocks that carry the token, newest first. Building the token's cache entry reads those blocks back to the newest that sets the metadata, with no bound, once per entry: on the first read of the token after the cache file is new, cleared or has evicted it, a list read included. Past the cached epochs, one request reads at most `max_scan_items` of those blocks across every token it reads. `/addresses/{address}/extended` splits the limit evenly among the units it lists that read a reference token (reference tokens and CIP-68 user tokens), in the order it lists them, the first ones a block more where it does not divide, so a unit that needs more blocks than its share answers as below whatever the other units need. Where the blocks within the limit set no metadata, the read answers the newest metadata tx it knows of without the others: a mint of the epochs past the cache whose CIP-25 metadata names the token, else the tx the cached epochs found. With no cache entry behind the read, because the token was first minted in an epoch a rollback can still reach or the cache is off or unavailable, the read walks the token's whole history within the limit, and past it answers no metadata tx unless such a mint names the token. The asset lists report the supply alone and walk no blocks past the cached epochs. With `storage.cache.enabled = false` the node registers no `assets` namespace, so no read builds an entry: the lists walk no blocks, and every other read stays within its limit. Whether an asset exists, and the slot of its first mint, come from the archive's entity index, which the seal writes for the first mint of every sealed epoch, and the staged first mints of the epochs not yet sealed: an asset in neither is not found, without folding anything.

An archive whose seals ran on an earlier version wrote no `asset` entries to the entity index, and a state store an earlier version synced stages a re-mint as a first mint. Before the first start of this version on such a store, run `dolos doctor rebuild-state --rewrite-logs`, or bootstrap again: the rebuild indexes every first mint from the start of the chain. Until then:

- an asset first minted in a sealed epoch is not found, unless it was minted or burned again in an epoch not yet sealed: then its first mint is that later mint or burn, and its supply and mint count are those since, a negative supply after a burn;
- the asset lists leave out each asset they name that is not found, and log a warning naming the rebuild;
- `dolos cache warm --namespace assets --scan` refuses to run, naming the rebuild;
- an epoch the node seals lists its re-mints as first mints, so the lists name those assets a second time.

The rebuild repairs all of it: it writes each first-mint list again where an earlier run sealed it from other rows, deletes such a list in an epoch where it finds no first mint, and leaves none of the old lists' rows behind. A read, or `dolos cache warm`, builds again any `assets` cache entry that started at a re-mint. A stele snapshot published by such a version still declares the `assets` state namespace; a restore refuses it by name, so bootstrap from a stele published by a version that carries the `asset` entries.

A rolling `history` window prunes the asset-mint logs by epoch and the entity index by slot. A pruned node does not find an asset first minted before its window, until the asset is minted or burned inside it: the node then takes that mint or burn for the first, reports the supply and mint count of the window's mints and burns alone, and lists the asset again. An asset first minted inside the window, but in the epoch the window starts in, is found and folded without that epoch's mints. A node without an archive keeps neither, so it finds only the assets first minted in its unsealed epochs, and takes a later mint or burn of an older asset for its first.

## DRep listing on stores synced by an older release

`/governance/dreps` lists every DRep a certificate of a valid tx ever named, vote-delegation targets and the special DReps included, in the order a certificate first named it, with the latest anchor a registration or update carried. It reads them from the `drep-sightings` state namespace, which the roll writes. A state store synced by a release without that namespace has no sightings for the blocks it applied before: it lists only the DReps certificates named since, at the position of that later certificate. Syncing forward does not recover what is behind the cursor; resync the instance, or bootstrap it from a snapshot that carries `state-drep-sightings`, to get the full list in its exact order.
