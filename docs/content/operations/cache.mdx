Dolos keeps a cache of answers it derives from its other stores, so that an expensive read is computed once rather than on every request. The cache is disposable: it is not part of the WAL, the state or the archive, it is left out of snapshots and restores, and deleting it changes no answer the node derives, only how fast the first requests are served. Its entries are not tied to a chain, though: when the chain under the same `storage.path` changes, as when a devnet is reset, clear the cache before starting the node, or it serves the old chain's answers. The exception is off-chain metadata, which the node does not derive: a cleared body is fetched again from its host, and is gone if the host no longer serves it.

## What it holds

The cache is split into namespaces, one per use. Each namespace has a format version; an upgrade that changes a namespace's encoding bumps it, and the entries kept under the old version are wiped when the node starts.

| namespace            | validity   | serves                                                                                                        |
| -------------------- | ---------- | ------------------------------------------------------------------------------------------------------------- |
| `totals`             | immutable  | the lifetime totals of `/addresses/{address}/total` and `/accounts/{stake_address}/addresses/total`           |
| `network`            | tip-scoped | the `/network` body, for 30 seconds                                                                           |
| `offchain`           | immutable  | the verified DRep metadata of `/governance/dreps` and `/governance/dreps/{drep_id}/metadata`, by content hash |
| `offchain-failures`  | tip-scoped | failed metadata fetches, for 10 minutes, so a dead host is not asked again on every request                   |
| `pool-registrations` | immutable  | where each pool first registered, for the order of `/pools` and `/pools/extended`                             |
| `pool-blocks`        | immutable  | each pool's lifetime blocks, for `blocks_minted` in `/pools/extended` and `/pools/{pool_id}`                  |

A namespace has one of two validity models:

- **Immutable** entries are never stale. An `offchain` body is pinned by its anchor's content hash, which every read checks again. The other immutable entries are built from sealed data only, so they are at most incomplete: a `totals` entry sums a credential's sealed epochs up to its _watermark_, the last epoch it covers, and a read adds the epochs after it. The `pool-registrations` and `pool-blocks` namespaces each hold one entry for every pool, up to the last slot or epoch no rollback can undo, and a read adds what came after. Once more epochs seal, the entry is extended in the background. Immutable entries are kept in memory and on disk.
- **Tip-scoped** entries are valid for a while. After that, a `network` entry is served stale while one rebuild replaces it, and an `offchain-failures` entry is ignored, so the next request fetches again. They are kept in memory only.

The disk tier is a single Redb file, `<storage.path>/cache/cache.redb`. Its writes skip the fsync, and the node makes them durable when it shuts down, so a crash loses at most the entries written since. A file found corrupt, cut short, or laid out by another release, such as one you rolled back from, is recreated empty; one that fails to open for another reason, such as its permissions, is an error and the node does not start.

## Budgets and admission

| setting                               | default           |
| ------------------------------------- | ----------------- |
| `storage.cache.memory_mb`             | `512` (MiB)       |
| `storage.cache.disk_mb`               | `4096` (MiB)      |
| `storage.cache.admission.<namespace>` | the namespace's own |

When a tier is full, it evicts the entries with the lowest build cost per byte first, and the least recently used among equals.

An entry is kept only if building it cost at least its namespace's admission threshold, so cheap answers do not crowd out expensive ones. A `totals` entry's cost is the number of per-epoch unit sums its build read, and it is kept from 100,000. Set `[storage.cache.admission]` to change a threshold, for example `totals = 20000` to keep more credentials. See the [`storage.cache`](../configuration/schema#storagecache) section for every setting.

## Footprint

These figures size the `totals` namespace on mainnet. They were measured with dolos `2.0.0-alpha.0` (commit `ec44940f`) on a store whose sealed epochs ran to 646, so every entry's watermark is epoch 646. Two key sets were measured:

- **Every key worth warming**: `dolos cache warm --namespace totals --scan`. It found 2,251 candidate credentials and kept 191; the other 2,060 cost less than the admission threshold.
- **A benchmark set** of 8 heavy and light addresses, payment credentials and stake addresses, warmed with `--keys`, of which 7 were kept.

| key set       | entries | entry bytes | cache file | `warm` took | memory tier |
| ------------- | ------- | ----------- | ---------- | ----------- | ----------- |
| `--scan`      | 191     | 539.0 MB    | 1.14 GB    | 92.8 s      | 539.0 MB    |
| benchmark set | 7       | 233.7 MB    | 671 MB     | 8.0 s       | 233.7 MB    |

- **Entry bytes** are what `dolos cache stats` reports and what `disk_mb` counts. The median entry is 119 KB; the largest, for the busiest credentials, are 47–88 MB.
- **The cache file** is larger than its entries: Redb rounds each large value up to a power of two and grows the file by doubling. Files written by `warm` measured 2.1 times their entry bytes for `--scan` and 2.9 times for the benchmark set; written with one durable commit per entry, the same sets measured 1.6 and 4.6 times. A running node commits durably only at shutdown, and until then Redb cannot reuse the pages of what was on disk when it started, so rewriting entries, such as `totals` entries refreshed after a seal, needs room for another copy of that content, and the file grows to make it. The growth levels off there rather than climbing with uptime, and a restart makes the space reusable. Leave room on disk for several times the disk budget. `clear` frees the space for reuse; the file shrinks only when nothing else sits after the freed pages, as when `totals` is the only namespace on disk.
- **`warm` took** the wall-clock time on an SSD. For `--scan`, the time `warm` prints leaves out its first pass over the sealed address rows to find the candidates, so it printed 14.6 s of the 92.8 s.
- **The memory tier** column is the tier's own accounting of the entries it held, keys plus values, which is what `memory_mb` counts. The tier held the whole benchmark set; the `--scan` figure is its entry bytes, which a node holding all of it would count. The process holds more than the tier, for the response buffers its allocator keeps.

All of `--scan` fits the 4 GiB default disk budget, and the benchmark set fits the 512 MiB default memory budget. All of `--scan` does not fit the memory budget: it exceeds 512 MiB (536,870,912 bytes) by 2.1 MB. Under the default, a node whose clients read every kept key serves its lowest cost-per-byte entries from the disk tier. To keep the whole namespace in memory, raise `storage.cache.memory_mb` above 514 (539 MB); the namespace grows with the chain, so leave headroom.

## Commands

The `dolos cache` commands work on the cache file directly, so they run with the node stopped. While a running node, or another `dolos` command, holds the cache file, they exit with an error asking you to stop it first. They print the cache's warnings, such as a cache file found corrupt and recreated empty, on stderr.

- `dolos cache warm --namespace <ns>` builds entries ahead of the requests that would miss them, keeping those at or above the admission threshold, and prints how many it kept, their bytes on disk and the time taken. It also counts the entries the disk budget refused or evicted, including entries already current that a later one evicted. It takes one source of keys, and builds a key listed twice once:
  - `--keys <file>`: one key per line. For `totals`, a key is an address, a payment credential (`addr_vkh…` or `script…`) or a stake address.
  - `--previous`: the keys the namespace held when it was last cleared, to restore a cache after `clear`.
  - `--scan`: the keys the namespace finds worth warming. For `totals`, every credential whose rows in a single sealed epoch reach 4,096 unit sums.

  `warm` makes its entries durable every 30 seconds. If it is interrupted, run it again: it skips the entries already current.
- `dolos cache clear --namespace <ns>` wipes one namespace, and `--all` every one. The keys they held are recorded for `warm --previous`.
- `dolos cache stats` prints each namespace's entries, bytes on disk, format version, and oldest and newest watermark. Hit rates are not kept on disk; read them from the metrics below.
- `dolos cache verify` rebuilds a random sample of entries without the cache, each up to its own watermark, and compares them by digest. It prints each mismatch and exits non-zero on any. `--namespace` checks one namespace, and `--sample` sets how many entries it rebuilds per namespace (100 by default).

`warm` and `verify` work on the namespaces that know how to build their entries offline, for now `totals`; given another, they name the ones they support.

## Metrics

The cache records OpenTelemetry metrics under the `dolos-cache` meter:

| metric            | kind      | attributes          |
| ----------------- | --------- | ------------------- |
| `cache_hits`      | counter   | `namespace`, `tier` |
| `cache_misses`    | counter   | `namespace`, `tier` |
| `cache_evictions` | counter   | `namespace`, `tier` |
| `cache_fills`     | counter   | `namespace`         |
| `cache_fill_time` | histogram | `namespace`, in seconds |
| `cache_entries`   | gauge     | `namespace`, `tier` |
| `cache_bytes`     | gauge     | `namespace`, `tier` |

`tier` is `memory` or `disk`; the disk tier's own evictions are not counted. A lookup reads the disk only after a memory miss, so a namespace's hit rate is its memory and disk hits over its hits and misses on the memory tier. The metrics reach a collector through the process's OpenTelemetry meter provider; the [`[telemetry]`](./tracing) section exports traces only, so `dolos daemon` does not export these metrics yet.

## Pruned nodes

The `totals` namespace sums sealed per-epoch stats from the archive, which a node with `history.mode = "rolling"` prunes. On such a node the namespace is off: the totals routes compute every answer without the cache, and `warm` and `verify` refuse it. Entries an earlier, unpruned run left on disk stay there until cleared: `stats` reports the namespace as off with their count, and `clear --namespace totals` or `clear --all` wipes them.

The `pool-registrations` and `pool-blocks` namespaces are built from the archive's certificates and per-epoch pool logs, and are off on such a node in the same way. They are off too while `storage.cache.enabled = false`, since an entry that is never kept would be rebuilt for every pool on every request: the pool routes then read the archive for the pools they answer about.
