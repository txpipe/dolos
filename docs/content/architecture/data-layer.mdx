Dolos keeps everything it needs on local disk in a handful of embedded stores — key-value engines for live data, plus append-only flatfiles for archived block bodies. Rather than one monolithic database, it uses several purpose-built stores — each optimized for a different access pattern — behind a common set of traits, so the underlying engine can be swapped without touching the rest of the system.

## The stores

Under the configured `storage.path`, a running node maintains three on-disk stores plus an in-memory (or persistent) mempool:

```
<storage.path>/
├── wal/       Write-Ahead Log — recent blocks as reversible deltas (rollback buffer)
├── state/     Ledger state — current UTxO set (with its by-address/asset/… tags), pools, accounts, epoch state, protocol params
└── archive/   Historical blocks — full block bodies, temporal entity logs, and the reverse lookups over them
```

| Store | Holds | Why it's separate |
| ----- | ----- | ----------------- |
| **WAL** | The most recent blocks, stored as `EntityDelta`s that can be applied or undone. | Rollbacks (chain reorganizations) are resolved by replaying these deltas in reverse. It is a bounded buffer, not long-term history. |
| **State** | The *current* ledger: UTxO set and its reverse-lookup tags (by address, payment credential, stake credential, policy, asset, reference script), stake pool registry, account/stake state, DReps, protocol parameters, and per-epoch ledger state. | This is the hot, always-current view the ledger rules read and write on every block. The tags are a projection of the UTxO set, so they live beside it and commit with it. |
| **Archive** | Immutable history: full block bodies, time-indexed logs of entity changes, and the reverse lookups over them — slots by address, payment credential, stake credential, policy, asset, datum and more, plus slot by block hash, block number and tx hash. | History is append-only and read differently from current state, so it uses its own layout (see below). The lookups are a projection of the blocks, so they live beside them and commit with them. |
| **Mempool** | Submitted-but-unconfirmed transactions and their lifecycle state. | Pending transactions are transient and overlaid on top of committed state during validation. |

## Store identity

Each on-disk state and archive store records, when it is created, the compatibility identifier of the contract the binary that created it writes: the current entry of the `compatibility` values the release reads (`v2-alpha.2` for this release). The state store keeps it under the key `identity` in its `state-cursor` keyspace; the archive keeps it in the `archive-meta` keyspace of its index database.

Every command that opens a state or archive store checks it before anything else:

- A store recording an identity the release reads opens.
- A store with no identity that holds nothing is new: it records the current identity before its first write.
- A store holding data but no identity, written before stores recorded one, is refused, and so is a store recording an identity the release does not read. The error names the store, its path and what it found.

The configuration plays no part, so no edit to `dolos.toml` gets a refused store past the check. The remedies are the ways to get stores the release writes itself:

- clear storage and re-sync: `dolos bootstrap relay --force` (or `dolos bootstrap mithril --force`), then `dolos daemon`;
- restore from a stele: `dolos bootstrap stelae --force`.

`dolos bootstrap` treats a refused store as data in the way: `--force` on its own clears it, and every other run of the command refuses with the same error, `--skip-if-data` and `--continue` included. `--force` clears only the storage root, though, and never a state store that fails to open for another reason, as a half-unpacked one does, or whose cursor fails to read. So beside a refused store it is refused too, naming what to remove by hand, while such a state is there, or while a directory the configuration keeps outside the root (an absolute or `..` `path`, or a `blocks_path` outside the root) holds data: a store with data, an archive that fails to open, or block segments. A directory holding no data, such as a fresh mount point or an empty store this release opens, doesn't stop it. A running node holds its stores, so they fail to open, and `--force` stops at the store's own error: stop the node first. A stele restore, a Mithril import and a relay sync write through the running binary's own stores, so what they produce records that binary's identity. A stele's own compatibility is settled by its media types and schemas, not by this identity. A Dolos snapshot (`dolos bootstrap snapshot`) unpacks the exporting node's stores as they were, so they are checked once unpacked, and a snapshot exported before stores recorded an identity is refused.

The WAL keeps its own format version, wiped when older and refused when newer. The mempool and the cache are outside the check.

## Storage traits and pluggable backends

Each store is defined as a trait in `dolos-core` — `WalStore`, `StateStore`, `ArchiveStore`, and `MempoolStore` — and the rest of Dolos only ever talks to those traits. Concrete implementations are selected at runtime in `src/adapters/storage.rs`, which wraps each backend in an enum, from each store's `type` in the configuration.

Available backends:

- **redb** (`dolos-redb3`) — an embedded ACID B+tree store. It backs the WAL (the only WAL implementation) and the persistent mempool. It is not a state or archive backend.
- **fjall** (`dolos-fjall`) — an LSM-tree engine tuned for write-heavy workloads with many hot keys. The only persistent backend for the state and archive stores (`type = "fjall"`), and the default for both. Its tuning comes from a named preset, `standard`.
- **in-memory** — non-persistent stores for testing and ephemeral nodes (`type = "ephemeral"`). State and archive have builtin implementations in `dolos-core` backed by ordered maps, which serve their traits in full; the WAL follows the state, in memory with an ephemeral state.
- **no-op** — an archive that silently discards writes, opened when the configuration keeps no history.

## Storage modes

The three storage modes are the values of `history.mode`:

| Mode | `history.mode` | Archive | Use case |
| ---- | -------------- | ------- | -------- |
| **Ledger-only** | `none` | none | Only the tip of the chain — smallest footprint, query-light deployments. |
| **Sliding history** | `rolling`, with a `window` | pruned to the window | Recent history for most dApp queries without a full archive. |
| **Full archive** | `full` (the default) | complete | The entire chain history — research, validation, explorers. |

`history.mode = "none"` is the ledger-only switch, and it drops the historical lookups with the archive that hosts them. The live-UTxO tags are not affected: they project the UTxO set, so they stay in the state store in every mode (2.94 GB on mainnet; see [The v2 data model](#the-v2-data-model)).

Pruning is driven by `prune_history()` on the WAL and archive stores. The WAL is always pruned to the protocol's rollback window. In the archive, pruning covers the block bodies, the logs, and the `archive-tags`, `index-exact` and `index-entity` keyspaces, so a sliding-history node's index footprint is window-sized too. A sliding-history node therefore keeps the first sightings of its window only, and a stele publisher keeps full history. See the [configuration schema](../configuration/schema#storage) for the exact keys, and for which store types combine.

## Data model primitives

A few concepts recur across the stores:

- **Namespaced entities.** State and archive data are organized into namespaces (UTxOs, pools, accounts, pending rewards, …), each a logical table keyed by an entity key. A store may hold a single value per key or multiple values per key.
- **Typed keys.** A key is a byte string of any length, and every namespace has one typed key struct that encodes and decodes it — a stake credential for accounts, a pool hash, a proposal's index and transaction, an empty key for a singleton. Readers and writers of a namespace both go through that struct, so they agree on its bytes, its prefixes and its order; a decode is exact, so a malformed key is an error rather than a near miss. Composite keys put fixed-width parts first, which keeps prefix scans sound.
- **`EntityDelta` (apply / undo).** Every state change is expressed as a delta that carries enough of the previous value to reverse itself. Applying deltas rolls the ledger forward; undoing them (from the WAL) rolls it back. This is the mechanism that makes rollbacks exact — see the [Sync Pipeline](./sync-pipeline).
- **`EpochValue` snapshot window.** Cardano staking reads state as it was several epochs ago. State entities that participate in staking are stored as a rotating window of snapshots (live / mark / set / go / next). The details are covered in the [Ledger Model](./ledger-model).
- **Archive dual storage.** Block bodies are written to append-only flatfile segments (one segment per Cardano epoch) as one zstd frame per block, compressed with the dictionary bundled in `dolos-flatfiles`, while a compact index maps each slot to its `(segment, offset, length)` frame location. Every frame is written and synced before the location that names it is committed, so a crash leaves at most dead space at a segment's end and never a location pointing at bytes that are not there. Historical entity changes are stored as `(slot, typed key) → value` logs, enabling range queries over time.
- **Period logs.** Folds over history that the API serves, such as the assets each epoch first minted, the scripts it first saw, the addresses each account saw, or what each address received and sent, are staged per block as state entities (`first-mints`, `first-scripts`, `asset-mints`, `account-addresses`, `address-stats`, `payment-addresses`, `payment-stats`, `account-stats`) and undone through the WAL like any other delta: insert-if-absent rows for lists, and sum rows whose undo subtracts. At each epoch boundary, ESTART seals every staged epoch that can no longer roll back, which is epoch E-2 on the public networks, into archive logs keyed by the epoch's start slot (`first-mint-chunks`, `policy-mint-chunks`, `first-script-chunks`, `asset-mint-chunks`, `account-address-chunks`, `address-stats`, `payment-address-chunks`, `account-stats`). A `Set` row is keyed exactly, by `group ‖ epoch ‖ member` where its group has a fixed width, so one prefix scan returns a group's staged epochs and nothing else. `AddressStats` and `AccountStats` are one type each in both stores, under one namespace: in state they are keyed `epoch ‖ key`, in the archive `epoch_start(e) ‖ key`, and the seal moves an epoch's rows from one to the other in chunks of rows, so a chunk may split an account's rows of an epoch between the stores. The seal commits the archive rows before it deletes the staged ones, and both before its cursor commit, so a crash re-runs the seal. Readers take the staged rows first and the sealed rows second, and the sealed row wins, so a seal running beside a read leaves its answer unchanged. `/assets`, `/assets/policy/{policy}` and `/scripts` page through these logs without decoding blocks, and so does `/accounts/{stake_address}/addresses`: an address active in several epochs is listed in each epoch's row, and the reader keeps its first appearance. `/assets/{asset}/history` reads the count off the first chunk of each epoch from the asset's first mint on, then loads only the chunks its page covers, so a deep page costs what the first one does. `/addresses/{address}/total` adds up an address's per-epoch rows; for a payment credential it reads the epoch's addresses from `payment-address-chunks`, or from `payment-addresses` while the epoch is unsealed, first. `/accounts/{stake_address}/addresses/total` point-reads the account's `account-stats` rows over the epoch range: each holds the account's distinct tx count for an epoch it was active in, so they give the tx count and name the epochs in which to scan the account's address rows, an `AccountKey` prefix range, merged key by key across the two stores. Pruning drops sealed rows by slot, like any other log. Rows are written only as blocks roll, so a store that applied blocks with a build lacking a log has no rows for those blocks; it gains their history by bootstrapping again, from a stele that carries the log, from Mithril or from a relay. Source: `crates/cardano/src/periods/`.
- **Metadata label counts.** `metadata-labels` (`MetadataLabelState`) holds one state row per transaction metadata label: the number of valid transactions that carry it, raised per block by a delta that a rollback undoes. The key is the label as 8 big-endian bytes, so a scan returns labels in numeric order up to 2^64 − 1. A phase-2-invalid transaction adds nothing, as db-sync writes no metadata row for one. The counts are all-time, so pruning leaves them, and they never seal into the archive. `/metadata/txs/labels` pages through the namespace. On mainnet it is 3.2 k rows, 19.59 kB on disk, carried in every stele's state tip. Source: `crates/cardano/src/model/metadata_labels.rs`.
- **API-only state.** A fact the API serves that the ledger rules never read lives in its own state namespace, so a ledger namespace holds only what the ledger knows. `drep-sightings` (`DRepSightingState`, keyed by `DRepKey`) holds one row per DRep a certificate of a valid tx has named, vote delegations and the special DReps included: the position of the first such certificate, down to its place in the tx, and the latest anchor a registration or update carried. `/governance/dreps` lists DReps in that order with that anchor, which is db-sync's order and metadata, and reads the page's `DRepState` rows for the rest. The ledger's own anchor is cleared by an update without one, and a DRep only a vote delegation named has no `DRepState` row. Its deltas undo through the WAL, and its rows are never pruned. On mainnet it holds 1.7 k rows, 130.20 kB on disk.
- **Index dimensions.** Tag multimaps keyed by values such as an address, a payment or stake credential, a policy id or an asset id; [The v2 data model](#the-v2-data-model) lists every dimension. The live ones point at the matching UTxOs and live in the state store's `state-tags` keyspace, written in the same batch as the UTxO set; the historical ones point at slots and live in the archive store's `archive-tags` keyspace, beside the `index-exact` keyspace that resolves a block hash, block number or transaction hash to its slot — both written in the same batch as the blocks they project.
- **Entity index.** The `index-entity` keyspace maps an entity's id to the slot it was first seen at, for the entity kinds the chain declares; Cardano declares `asset` (its 32-byte `AssetKey`), `script` (its 28-byte hash) and `stake` (a credential's 29-byte stake address, the key its `stake` tag files it under). Core names no kind. The seal of an immutable epoch writes it in the same commit as the epoch's sealed logs, nothing undoes it because no rollback reaches a sealed epoch, and a prune sweeps it by slot. Steles carry it as one `entity-{kind}` layer per kind and epoch, available from the stele cut two boundaries after the epoch. Source: `crates/core/src/{indexes,archive}.rs`, `crates/fjall/src/archive/entity.rs`, `crates/cardano/src/indexes/entities.rs`.

The two fjall databases and their keyspaces:

| Store | Keyspaces | One batch commits |
|---|---|---|
| state | `state-cursor`, `state-utxos`, `state-entities`, `state-tags` | entities + UTxO set + live-UTxO tags + cursor |
| archive | `archive-blocks`, `archive-logs`, `archive-tags`, `index-exact`, `index-entity`, `archive-meta` | block locations + logs + archive tags + exact lookups + entity index entries |

The [store identity](#store-identity) is written once, when the store is created, beside the cursor in `state-cursor` and alone in `archive-meta`.

Source: `crates/core/src/{state,archive,wal,indexes,mempool}.rs`, `crates/redb3/src/*`, `crates/fjall/src/*`, and storage configuration in `crates/core/src/config.rs`.

## Entity naming

The Cardano entity types in `crates/cardano/src/model/` follow one naming convention, so a type's name says how its rows behave and its namespace says what one row is.

**The suffix names the stereotype.**

| Suffix | One row is | Changes by | Stores |
| ------ | ---------- | ---------- | ------ |
| `State` | the current state of one ledger object | deltas | state; `EpochState` also writes one archive row per epoch |
| `Log` | a boundary's record for one object | one write at a boundary | archive |
| `Stats` | an additive per-epoch aggregate for one key | a sum staged per block | state until its epoch seals, then archive |
| `Set` | a member's first appearance in an epoch | an insert-if-absent staged per block | state only; its seal builds a `Chunk` |
| `Chunk` | a page of an ordered list, built at seal | one write at seal | archive |

A `Stats` type is one type under one namespace in both stores: its seal moves an epoch's rows to the archive at the epoch's start slot, and never reshapes them. On mainnet, the archive's `account-stats` takes 1.12 GB on disk for 33.9 M rows, and its `address-stats` 18.70 GB for 104.4 M rows; [The v2 data model](#the-v2-data-model) gives every structure's footprint.

A `Set` lives in state only, one row per member keyed `group ‖ epoch ‖ member` (`GroupKey`), so one prefix scan returns a group's unsealed epochs. Its seal builds a `Chunk`: one list per group and epoch, written to the archive at the epoch's start slot before the epoch's `Set` rows are deleted. A seal may drop rows, as first mints drop re-mints. A `Set` and the `Stats` that counts its group may seal into one `Chunk`, and that `Stats` then lives in state only: `PaymentStats` does, its tx count riding in `PaymentAddressChunk` beside the addresses.

| Set, in state | Chunk, in the archive | Serves | Chunk on disk, mainnet |
| ------------- | --------------------- | ------ | ---------------------- |
| `account-addresses` (`AccountAddressSet`) | `account-address-chunks` (`AccountAddressChunk`) | `/accounts/{stake_address}/addresses` | 3.06 GB |
| `payment-addresses` (`PaymentAddressSet`), with `payment-stats` (`PaymentStats`) | `payment-address-chunks` (`PaymentAddressChunk`) | `/addresses/{address}/total` by payment credential | 4.93 GB |
| `first-mints` (`FirstMintSet`) | `first-mint-chunks` (`FirstMintChunk`) | `/assets` | 128.30 MB |
| `first-scripts` (`FirstScriptSet`) | `first-script-chunks` (`FirstScriptChunk`) | `/scripts` | 9.85 MB |
| | `policy-mint-chunks` (`PolicyMintChunk`) | `/assets/policy/{policy}` | 90.19 MB |
| `asset-mints` (`AssetMintSet`) | `asset-mint-chunks` (`AssetMintChunk`) | `/assets/{asset}/history` | 1.18 GB |

The sizes are each chunk namespace's compacted footprint on mainnet, measured as [The v2 data model](#the-v2-data-model) describes.

A `Set` lists a member once per epoch, so a list that names each member once over all of history needs a witness to tell a first appearance from a repeat. No state namespace records what first mints and scripts have been seen, so their witness is the archive's entity index for the sealed epochs, which the seal writes for every first mint and script it seals before it deletes the staged row, and the staged rows of the epochs not yet sealed (decision 0064). The roll reads both once per batch for the assets the batch mints and the scripts it carries, taking only index entries below the batch's first slot, so a re-roll over an archive that already indexes the batch (`dolos doctor rebuild-state`) never reads the batch's own entries, and the staged rows are exact: a `first-mints` row is an asset's first mint ever. `/scripts/{script_hash}` reads the index, then the staged rows, then the index again, and decodes the block they name; an asset read finds its first mint the same way, and answers 404 where neither holds it. `first-scripts` has no group, so its rows key `epoch ‖ script hash`. The `account-addresses` seal records each sealed account's first slot under its stake address too: that entry, not a `stake` tag seek, is what `/accounts/{stake_address}` reads for a credential state no longer holds, and the tag answers only for the epochs not yet sealed, from the first of them on.

**Vocabulary.** *Account* is a stake credential, *payment* is a payment credential and *address* is a whole address. *Stake* names only an amount of stake, so a pool's record for one epoch is a `PoolEpochLog`, not a stake log.

**Keys.** Each identity has one key type, named `{Thing}Key`: `AccountKey`, `PoolKey`, `EraKey` (an era's protocol version), and so on. A key that groups others is the prefix of the keys it groups. `AddressKey` keys an address stake-first: `AccountKey ‖ rest` for an address with a stake credential, `rest` being the address without its stake hash (a base address's header and payment hash, a stake address's header), and `0x00 ‖ address` for any other. An `AccountKey` opens with its CBOR header `0x82`, so the first byte tells the two forms apart, and an account's addresses are its prefix range.

**Namespaces** are kebab-case and name the plural of what one row is: `eras` holds `EraState` rows, `pool-epochs` holds `PoolEpochLog` rows, and `pending-rewards` and `pending-mirs` hold `PendingRewardState` and `PendingMirState` rows. `gov` stays singular. The state store registers the namespaces of the types declared with a state key (`State`, `Stats` and `Set`), and the archive registers those declared with a log key, so an archive-only `Log` or `Chunk` has no state namespace. A stele carries each namespace verbatim in its kind, `state-{ns}` for a state namespace and `log-{ns}` for a log namespace, and `dolos data dump-state` and `dolos data dump-logs` take the namespace as their argument.

## The v2 data model

The v2 data model is frozen: the structures below are everything the state and archive stores hold, and a store this release writes holds no row outside them. Each has a measured footprint on mainnet.

**Where the footprints come from.** Every footprint was measured on one mainnet store, built from genesis by a Mithril import with dolos [`8ed6402d`](https://github.com/txpipe/dolos/commit/8ed6402d8f0eda2bf71b2574adaa9c43c961a4d4) to slot 201,592,762 in epoch 664. Each structure's rows were copied, unchanged, into a fjall 3.1 keyspace of their own, laid out as a fully compacted default keyspace (LZ4 data blocks, partitioned index and filter), and the keyspace's size was read. Sizes are decimal (1 GB = 10⁹ bytes). A live store is larger, because its uncompacted levels and journals overlap: this one took 7.19 GB of state and 108.22 GB of archive index on disk, against 5.03 GB and 93.16 GB compacted. Block bodies are outside these figures; on mainnet their segments took 92.60 GiB.

| `state-utxos` | 1.65 GB |
| `state-entities` | 0.44 GB |
| `state-tags` | 2.94 GB |
| `archive-logs` | 64.31 GB |
| `archive-tags` | 22.07 GB |

| `index-entity` | 0.70 GB |
| `archive-blocks` | 0.18 GB |

`state-cursor` and `archive-meta` hold the cursor and the [store identity](#store-identity), a few bytes each.

### Archive tag dimensions

`archive-tags` is keyed `dim_hash(8) ‖ xxh3_64(key)(8) ‖ slot(8)`, with `dim_hash = xxh3_64("block:" + dimension)` and an empty value. A tag says that the block at the slot touches the key. A phase-2-invalid transaction contributes its collateral inputs and collateral return, never its ordinary inputs and outputs, and none of its witness or auxiliary scripts. The rest of what it carries is tagged: its metadata labels, certificates, withdrawals, witness and redeemer datums, votes, and the scripts its redeemers execute, except spend redeemers, which name ordinary inputs and so stay untagged. A reader that answers for valid transactions only filters these tags; a datum lookup does not, and serves a datum an invalid transaction carried.

### The UTxO layouts

**The UTxO value**, in `state-utxos`, is CBOR `[era, body, slot, tx_index]`: era 6, body `a0`, slot 1000 and tx 3 encode as `84 06 41a0 1903e8 03`. A UTxO no block produced (genesis, AVVM or configured) stores `[era, body]`, as `82 06 41a0`. Decoding refuses trailing bytes. Its footprint is the `utxos` row above.

**The live-UTxO tags**, in `state-tags`, are keyed `dim_hash(8) ‖ lookup key ‖ slot(8, BE) ‖ tx_index + 1 (2, BE) ‖ txo_ref(36)`, with `dim_hash = xxh3_64("utxo:" + dimension)` and an empty value. The lookup key is stored whole, and a UTxO without a position writes ten zero bytes for its slot and index. The dimensions derive the same way as the archive's address and asset tags.

|---|---:|---:|
| `address` | 10.9 M | 708.18 MB |
| `payment` | 10.5 M | 556.16 MB |
| `stake` | 9.5 M | 465.67 MB |
| `policy` | 10.9 M | 446.16 MB |
| `asset` | 18.3 M | 764.98 MB |
| `script_ref` | 6.3 k | 466.44 kB |

The widest keys are Byron addresses: 17 live UTxOs sit at addresses of 3 kB to 22.6 kB, so the `address` live tag and the `address-stats` log reach keys of about 22.6 kB.

### The compatibility identity

The data model above is the contract `v2-alpha.2`, the one compatibility identifier this release reads. It replaces `v2-alpha.1` in a one-time amendment of the frozen model, which removed fields, renumbered others to close their index gaps and cleared the sync cursors from published rows, so a store recording `v2-alpha.1` is refused and rebuilt. Each state and archive store records it when created, under `identity` in `state-cursor` and in `archive-meta`, and a store holding data that records none, or one recording another, is refused at open, as [Store identity](#store-identity) describes.

### New eras

A new era, such as Dijkstra or Leios, may add to the data model without changing the contract: new namespaces, new tag dimensions, new protocol-parameter variants, and new fields at new CBOR indices. Anything beyond that, such as a changed key, a removed or renumbered field, or a reshaped value, is a break that waits for the next major version, v3.
