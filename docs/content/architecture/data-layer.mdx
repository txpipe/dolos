Dolos keeps everything it needs on local disk in a handful of embedded stores — key-value engines for live data, plus append-only flatfiles for archived block bodies. Rather than one monolithic database, it uses several purpose-built stores — each optimized for a different access pattern — behind a common set of traits, so the underlying engine can be swapped without touching the rest of the system.

## The stores

Under the configured `storage.path`, a running node maintains three on-disk stores plus an in-memory (or persistent) mempool:

```
<storage.path>/
├── wal/       Write-Ahead Log — recent blocks as reversible deltas (rollback buffer)
├── state/     Ledger state — current UTxO set (with its by-address/asset/… tags), pools, accounts, epoch state, protocol params
└── archive/   Historical blocks — full block bodies, temporal entity logs, and the reverse lookups over them
```

| Store | Holds | Why it's separate |
| ----- | ----- | ----------------- |
| **WAL** | The most recent blocks, stored as `EntityDelta`s that can be applied or undone. | Rollbacks (chain reorganizations) are resolved by replaying these deltas in reverse. It is a bounded buffer, not long-term history. |
| **State** | The *current* ledger: UTxO set and its reverse-lookup tags (by address, payment credential, stake credential, policy, asset, reference script), stake pool registry, account/stake state, DReps, protocol parameters, and per-epoch ledger state. | This is the hot, always-current view the ledger rules read and write on every block. The tags are a projection of the UTxO set, so they live beside it and commit with it. |
| **Archive** | Immutable history: full block bodies, time-indexed logs of entity changes, and the reverse lookups over them — slots by address, payment credential, stake credential, policy, asset, datum and more, plus slot by block hash, block number and tx hash. | History is append-only and read differently from current state, so it uses its own layout (see below). The lookups are a projection of the blocks, so they live beside them and commit with them. |
| **Mempool** | Submitted-but-unconfirmed transactions and their lifecycle state. | Pending transactions are transient and overlaid on top of committed state during validation. |

## Store identity

Each on-disk state and archive store records, when it is created, the compatibility identifier of the contract the binary that created it writes: the current entry of the `compatibility` values the release reads (`v2-alpha.1` for this release). The state store keeps it under the key `identity` in its `state-cursor` keyspace; the archive keeps it in the `archive-meta` keyspace of its index database.

Every command that opens a state or archive store checks it before anything else:

- A store recording an identity the release reads opens.
- A store with no identity that holds nothing is new: it records the current identity before its first write.
- A store holding data but no identity, written before stores recorded one, is refused, and so is a store recording an identity the release does not read. The error names the store, its path and what it found.

The configuration plays no part, so no edit to `dolos.toml` gets a refused store past the check. The remedies are the ways to get stores the release writes itself:

- clear storage and re-sync: `dolos bootstrap relay --force` (or `dolos bootstrap mithril --force`), then `dolos daemon`;
- restore from a stele: `dolos bootstrap stelae --force`.

`dolos bootstrap` treats a refused store as data in the way: `--force` on its own clears it, and every other run of the command refuses with the same error, `--skip-if-data` and `--continue` included. `--force` clears only the storage root, and no state it can't open, so beside a refused store it is refused too, naming what to remove by hand, while the configuration keeps a state or archive directory outside the root (an absolute or `..` `path`, or a `blocks_path` outside the root), or while the state fails to open for another reason, as a running node's does. A stele restore, a Mithril import and a relay sync write through the running binary's own stores, so what they produce records that binary's identity. A stele's own compatibility is settled by its media types and schemas, not by this identity. A Dolos snapshot (`dolos bootstrap snapshot`) unpacks the exporting node's stores as they were, so they are checked once unpacked, and a snapshot exported before stores recorded an identity is refused.

The WAL keeps its own format version, wiped when older and refused when newer. The mempool and the cache are outside the check.

## Storage traits and pluggable backends

Each store is defined as a trait in `dolos-core` — `WalStore`, `StateStore`, `ArchiveStore`, and `MempoolStore` — and the rest of Dolos only ever talks to those traits. Concrete implementations are selected at runtime in `src/adapters/storage.rs`, which wraps each backend in an enum so a node can mix engines per store.

Available backends:

- **redb** (`dolos-redb3`) — an embedded ACID B+tree store. It backs the WAL (the only WAL implementation) and the mempool. It is not a state or archive backend.
- **fjall** (`dolos-fjall`) — an LSM-tree engine tuned for write-heavy workloads with many hot keys. The only persistent backend for the state and archive stores, and the default for both.
- **no-op** — a store that silently discards writes, used to *disable* the archive.
- **in-memory** — non-persistent stores for testing and ephemeral nodes. State and archive have builtin implementations in `dolos-core` backed by ordered maps, which serve their traits in full; the WAL and mempool use redb's memory backend instead.

## Storage modes

The three storage modes exposed in configuration are really combinations of backend selection and history-pruning limits:

| Mode | Archive | History | Use case |
| ---- | ------- | ------- | -------- |
| **Ledger-only** | no-op | none | Only the tip of the chain — smallest footprint, query-light deployments. |
| **Sliding history** | enabled, pruned | a rolling window (`sync.max_history`) | Recent history for most dApp queries without a full archive. |
| **Full archive** | enabled, unpruned | complete | The entire chain history — research, validation, explorers. |

`archive.backend = "no_op"` is the ledger-only switch, and it drops the historical lookups with the archive that hosts them. The live-UTxO tags are not affected: they project the UTxO set, so they stay in the state store in every mode (about 3.5 GB on mainnet).

Pruning is driven by `prune_history()` on the WAL and archive stores. In the archive it covers the block bodies, the logs, and the `archive-tags` and `index-exact` keyspaces, so a sliding-history node's index footprint is window-sized too. See the [configuration schema](../configuration/schema#storage-section) for the exact keys.

## Data model primitives

A few concepts recur across the stores:

- **Namespaced entities.** State and archive data are organized into namespaces (UTxOs, pools, accounts, rewards, …), each a logical table keyed by an entity key. A store may hold a single value per key or multiple values per key.
- **Typed keys.** A key is a byte string of any length, and every namespace has one typed key struct that encodes and decodes it — a stake credential for accounts, a pool hash, a proposal's index and transaction, an empty key for a singleton. Readers and writers of a namespace both go through that struct, so they agree on its bytes, its prefixes and its order; a decode is exact, so a malformed key is an error rather than a near miss. Composite keys put fixed-width parts first, which keeps prefix scans sound.
- **`EntityDelta` (apply / undo).** Every state change is expressed as a delta that carries enough of the previous value to reverse itself. Applying deltas rolls the ledger forward; undoing them (from the WAL) rolls it back. This is the mechanism that makes rollbacks exact — see the [Sync Pipeline](./sync-pipeline).
- **`EpochValue` snapshot window.** Cardano staking reads state as it was several epochs ago. State entities that participate in staking are stored as a rotating window of snapshots (live / mark / set / go / next). The details are covered in the [Ledger Model](./ledger-model).
- **Archive dual storage.** Block bodies are written to append-only flatfile segments (one segment per Cardano epoch) as one zstd frame per block, compressed with the dictionary bundled in `dolos-flatfiles`, while a compact index maps each slot to its `(segment, offset, length)` frame location. Every frame is written and synced before the location that names it is committed, so a crash leaves at most dead space at a segment's end and never a location pointing at bytes that are not there. Historical entity changes are stored as `(slot, typed key) → value` logs, enabling range queries over time.
- **Period logs.** Folds over history that the API serves, such as the assets each epoch first minted, the scripts it first saw, the addresses each account saw, or what each address received and sent, are staged per block as state entities (`first-mints`, `first-scripts`, `asset-mints`, `account-addresses`, `address-stats`, `payment-addresses`, `payment-stats`, `account-stats`) and undone through the WAL like any other delta: insert-if-absent rows for lists, and sum rows whose undo subtracts. At each epoch boundary, ESTART seals every staged epoch that can no longer roll back, which is epoch E-2 on the public networks, into archive logs keyed by the epoch's start slot (`first-mint-chunks`, `policy-mint-chunks`, `first-script-chunks`, `asset-mint-chunks`, `account-address-chunks`, `address-stats`, `payment-address-chunks`, `account-stats`). A `Set` row is keyed exactly, by `group ‖ epoch ‖ member` where its group has a fixed width, so one prefix scan returns a group's staged epochs and nothing else. `AddressStats` and `AccountStats` are one type each in both stores, under one namespace: in state they are keyed `epoch ‖ key`, in the archive `epoch_start(e) ‖ key`, and the seal moves an epoch's rows from one to the other in chunks of rows, so a chunk may split an account's rows of an epoch between the stores. The seal commits the archive rows before it deletes the staged ones, and both before its cursor commit, so a crash re-runs the seal. Readers take the staged rows first and the sealed rows second, and the sealed row wins, so a seal running beside a read leaves its answer unchanged. `/assets`, `/assets/policy/{policy}` and `/scripts` page through these logs without decoding blocks, and so does `/accounts/{stake_address}/addresses`: an address active in several epochs is listed in each epoch's row, and the reader keeps its first appearance. `/assets/{asset}/history` reads the count off the first chunk of each epoch from the asset's first mint on, then loads only the chunks its page covers, so a deep page costs what the first one does. `/addresses/{address}/total` adds up an address's per-epoch rows; for a payment credential it reads the epoch's addresses from `payment-address-chunks`, or from `payment-addresses` while the epoch is unsealed, first. `/accounts/{stake_address}/addresses/total` point-reads the account's `account-stats` rows over the epoch range: each holds the account's distinct tx count for an epoch it was active in, so they give the tx count and name the epochs in which to scan the account's address rows, an `AccountKey` prefix range, merged key by key across the two stores. Pruning drops sealed rows by slot, like any other log. Rows are written only as blocks roll, so a store that applied blocks with a build lacking a log has no rows for those blocks; it gains their history by bootstrapping again, from a stele that carries the log, from Mithril or from a relay. Source: `crates/cardano/src/periods/`.
- **Metadata label counts.** `metadata-labels` (`MetadataLabelState`) holds one state row per transaction metadata label: the number of valid transactions that carry it, raised per block by a delta that a rollback undoes. The key is the label as 8 big-endian bytes, so a scan returns labels in numeric order up to 2^64 − 1. A phase-2-invalid transaction adds nothing, as db-sync writes no metadata row for one. The counts are all-time, so pruning leaves them, and they never seal into the archive. `/metadata/txs/labels` pages through the namespace. On mainnet it is 3,199 rows, 25.1 kB on disk, carried in every stele's state tip. Source: `crates/cardano/src/model/metadata_labels.rs`.
- **API-only state.** A fact the API serves that the ledger rules never read lives in its own state namespace, so a ledger namespace holds only what the ledger knows. `drep-sightings` (`DRepSightingState`, keyed by `DRepKey`) holds one row per DRep a certificate of a valid tx has named, vote delegations and the special DReps included: the position of the first such certificate, down to its place in the tx, and the latest anchor a registration or update carried. `/governance/dreps` lists DReps in that order with that anchor, which is db-sync's order and metadata, and reads the page's `DRepState` rows for the rest. The ledger's own anchor is cleared by an update without one, and a DRep only a vote delegation named has no `DRepState` row. Its deltas undo through the WAL, and its rows are never pruned. On mainnet it holds 1,700 rows, 128 kB on disk.
- **Index dimensions.** Tag multimaps keyed by address, payment credential, stake credential, policy id, and asset id. The live ones point at the matching UTxOs and live in the state store's `state-tags` keyspace, written in the same batch as the UTxO set; the historical ones point at slots and live in the archive store's `archive-tags` keyspace, beside the `index-exact` keyspace that resolves a block hash, block number or transaction hash to its slot — both written in the same batch as the blocks they project.

The two fjall databases and their keyspaces:

| Store | Keyspaces | One batch commits |
|---|---|---|
| state | `state-cursor`, `state-utxos`, `state-entities`, `state-tags` | entities + UTxO set + live-UTxO tags + cursor |
| archive | `archive-blocks`, `archive-logs`, `archive-tags`, `index-exact`, `archive-meta` | block locations + logs + archive tags + exact lookups |

The [store identity](#store-identity) is written once, when the store is created, beside the cursor in `state-cursor` and alone in `archive-meta`.

Source: `crates/core/src/{state,archive,wal,indexes,mempool}.rs`, `crates/redb3/src/*`, `crates/fjall/src/*`, and storage configuration in `crates/core/src/config.rs`.

## Entity naming

The Cardano entity types in `crates/cardano/src/model/` follow one naming convention, so a type's name says how its rows behave and its namespace says what one row is.

**The suffix names the stereotype.**

| Suffix | One row is | Changes by | Stores |
| ------ | ---------- | ---------- | ------ |
| `State` | the current state of one ledger object | deltas | state; `EpochState` also writes one archive row per epoch |
| `Log` | a boundary's record for one object | one write at a boundary | archive |
| `Stats` | an additive per-epoch aggregate for one key | a sum staged per block | state until its epoch seals, then archive |
| `Set` | a member's first appearance in an epoch | an insert-if-absent staged per block | state only; its seal builds a `Chunk` |
| `Chunk` | a page of an ordered list, built at seal | one write at seal | archive |

A `Stats` type is one type under one namespace in both stores: its seal moves an epoch's rows to the archive at the epoch's start slot, and never reshapes them. On mainnet, `account-stats` takes 1.16 GB on disk for 33.4 M rows, measured as the chunk sizes below are. `address-stats` holds 35.04 GB of raw rows for 103.2 M (epoch, address) pairs, counted over a full mainnet replay; its compacted size on disk has not been measured.

A `Set` lives in state only, one row per member keyed `group ‖ epoch ‖ member` (`GroupKey`), so one prefix scan returns a group's unsealed epochs. Its seal builds a `Chunk`: one list per group and epoch, written to the archive at the epoch's start slot before the epoch's `Set` rows are deleted. A seal may drop rows, as first mints drop re-mints. A `Set` and the `Stats` that counts its group may seal into one `Chunk`, and that `Stats` then lives in state only: `PaymentStats` does, its tx count riding in `PaymentAddressChunk` beside the addresses.

| Set, in state | Chunk, in the archive | Serves | Chunk on disk, mainnet |
| ------------- | --------------------- | ------ | ---------------------- |
| `account-addresses` (`AccountAddressSet`) | `account-address-chunks` (`AccountAddressChunk`) | `/accounts/{stake_address}/addresses` | 3.27 GB |
| `payment-addresses` (`PaymentAddressSet`), with `payment-stats` (`PaymentStats`) | `payment-address-chunks` (`PaymentAddressChunk`) | `/addresses/{address}/total` by payment credential | 5.27 GB |
| `first-mints` (`FirstMintSet`) | `first-mint-chunks` (`FirstMintChunk`) | `/assets` | 0.13 GB |
| `first-scripts` (`FirstScriptSet`) | `first-script-chunks` (`FirstScriptChunk`) | `/scripts` | 9.8 MB |
| | `policy-mint-chunks` (`PolicyMintChunk`) | `/assets/policy/{policy}` | 0.09 GB |
| `asset-mints` (`AssetMintSet`) | `asset-mint-chunks` (`AssetMintChunk`) | `/assets/{asset}/history` | 1.21 GB |

The sizes are the table files of each chunk namespace written at mainnet scale into a fully compacted fjall 3.1 store, measured under the namespace's earlier name (`stake-addresses`, `payment-stats` and `policy-first-mints`); renaming it left its keys and values unchanged. `first-mint-chunks` was built from mainnet's 11,159,935 first mints through epoch 646. `first-script-chunks` was measured in the endpoint-structures research, over mainnet's 319,671 scripts. `asset-mint-chunks` was measured under its own name, beside 0.26 MB of `asset-mints` staged in state at the tip.

A `Set` lists a member once per epoch, so a list that names each member once over all of history needs a witness to tell a first appearance from a repeat. First mints use `AssetState.initial_slot`. Scripts have no ledger state, so `scripts` (`ScriptState`) is their witness: one row per script hash, holding where the script was first seen (slot, tx index and order within the tx, in cardano-db-sync's order), written once and never pruned. It is 12.9 MB on mainnet and travels in every stele. `/scripts/{script_hash}` starts its lookup from it. `first-scripts` has no group, so its rows key `epoch ‖ script hash`.

**Vocabulary.** *Account* is a stake credential, *payment* is a payment credential and *address* is a whole address. *Stake* names only an amount of stake, so a pool's record for one epoch is a `PoolEpochLog`, not a stake log.

**Keys.** Each identity has one key type, named `{Thing}Key`: `AccountKey`, `PoolKey`, `EraKey` (an era's protocol version), and so on. A key that groups others is the prefix of the keys it groups. `AddressKey` keys an address stake-first: `AccountKey ‖ rest` for an address with a stake credential, `rest` being the address without its stake hash (a base address's header and payment hash, a stake address's header), and `0x00 ‖ address` for any other. An `AccountKey` opens with its CBOR header `0x82`, so the first byte tells the two forms apart, and an account's addresses are its prefix range.

**Namespaces** are kebab-case and name the plural of what one row is: `eras` holds `EraState` rows, `pool-epochs` holds `PoolEpochLog` rows, and `pending-rewards` and `pending-mirs` hold `PendingRewardState` and `PendingMirState` rows. `gov` stays singular. The state store registers the namespaces of the types declared with a state key (`State`, `Stats` and `Set`), and the archive registers those declared with a log key, so an archive-only `Log` or `Chunk` has no state namespace. A stele carries each namespace verbatim in its kind, `state-{ns}` for a state namespace and `log-{ns}` for a log namespace, and `dolos data dump-state` and `dolos data dump-logs` take the namespace as their argument.
